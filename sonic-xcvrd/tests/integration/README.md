# xcvrd integration tests (real `swsscommon` + redis)

These tests exercise the ASIC-readiness checker and the publishing workers against the real
`python3-swsscommon` binding and real redis instances (one per emulated namespace, SonicDBConfig
global configuration), which the unit tests cannot: initial snapshot replay and `Select` readiness,
the empty-`pop()` representation, the `DEL` event of the real binding, `removeSelectable()`, release
of the subscription connection, `ProducerStateTable` writes into the per-namespace APPL_DB, and the
real `SIGTERM` path of a daemon process.

Run them in their own pytest process (the unit-test module replaces `swsscommon` classes by mocks at
import time; the session fixture refuses to start if it finds them):

    XCVRD_INTEGRATION=1 python3 -m pytest -q -o addopts="" tests/integration
    XCVRD_IT_DURATION=300 XCVRD_INTEGRATION=1 python3 -m pytest -q -o addopts="" tests/integration -k cost   # full 5 min checker-cost run

They need `XCVRD_INTEGRATION=1`, `redis-server` and `redis-cli` on `PATH`; otherwise the directory is
not collected and an explicitly selected test file is skipped at module level (upstream CI has no redis).
The measured numbers of a run are appended to `$XCVRD_IT_RESULTS` (default: a run-scoped file in the
temp directory, printed at the end of the run).

Emulation and its limits:

- namespaces are emulated with one `redis-server` per namespace and a SonicDBConfig **global** configuration, so
  `daemon_base.db_connect()` and the workers' table helpers run unpatched; `sonic_py_common.multi_asic` is patched to
  report two front-end namespaces; the platform is a fake chassis with flat-memory QSFP-DD modules whose EEPROM reads
  succeed unless a test clears a module's `readable` flag, whose DOM thresholds and sensor values are fixed, and whose
  presence a test may change without an event (`get_change_event()` delivers queued events only; an idle poll answers
  status `True`, or `(False, {})` for a chassis built with `idle_status=False`); each module records the thread of
  every presence read; a test may hold the publishing worker inside a poll (`hold_next_change_event()`) or at the end
  of its admission pass before the mark (`DaemonRun.hold_mark_admitted()`);
  the media-settings lookup is stubbed to a fixed SI payload;
- the "nothing published before the marker" oracle reads the **producer** side of APPL_DB (`_PORT_TABLE:*` hashes
  written by `ProducerStateTable`); no `ConsumerStateTable` round trip is performed, so orchagent-side consumption is
  not exercised here;
- the CMIS-gate oracles are the STATE_DB `cmis_state` and the thread recorded by each fake module for every presence
  read (the device accessors are also used by the permitted threshold reads); the steady-state comparison covers the
  DB content and the publications, not the module handling: the fake modules are flat-memory, so the CMIS worker
  writes nothing to them, and the SFF manager is not enabled; the DOM worker runs but its per-port poll on the healthy namespace is not measured (the healthy-side cost
  oracle is a worker-like select loop in the test process); the RSS check is coarse (`ru_maxrss`), the weakref checks
  are unit tests;
- a daemon test that fails keeps its daemon's redis connections alive through pytest's traceback (about 500 descriptors
  per daemon), so under the default `ulimit -n 1024` a later daemon test can fail with "Too many open files": run with
  `ulimit -n 4096` when triaging a failure;
- the daemon tests run the daemon in-process (thread + `stop_event`); only the `SIGTERM` test uses a subprocess with a real signal; the
  base-tree A/B comparison of the shutdown time is not part of the suite;
- the heartbeat case drives the checker's clock (`xcvrd.xcvrd.time`) with a shim; the recorder and test clocks are real;
- the checker-cost limits are checker CPU < 5 %, `ru_maxrss` growth < 2 MB and checker exit ≤ 2 s after the last marker; `ru_maxrss` is the process-wide peak, so the RSS figure is coarse.

The numbers of a run are written to `$XCVRD_IT_RESULTS` (above); the figures recorded for the submitted series,
with the versions used, are in the pull request description.
